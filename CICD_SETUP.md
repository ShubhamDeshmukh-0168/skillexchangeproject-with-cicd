# Full Automation Setup — From Zero

One workflow, one trigger: **push to `main`** (or click "Run workflow" in
the Actions tab). From there it runs, in order:

1. **Terraform** creates/updates the VPC, EC2 app server, and RDS database
   — the DB password is generated automatically and never leaves AWS
2. **Build** compiles the WAR with Maven
3. **Docker** builds & pushes a versioned image to GitHub Container Registry
4. **Deploy** uploads the WAR to S3, then tells the EC2 instance to pull
   and install it via **AWS Systems Manager** (no SSH, no open port 22,
   no key pair anywhere) — restarts Tomcat, health-checks it, and rolls
   back automatically if the health check fails

Nothing is typed into a `.env` file or committed to the repo. The only
two secrets that exist are the credentials that let GitHub Actions act as
you in AWS — everything downstream of that (DB password, server access,
deploy mechanism) is generated or handled automatically.

The workflow file is `.github/workflows/full-deploy.yml`.

---

## Step 0 — One-time manual setup

Only one thing can't be automated away: AWS needs to trust GitHub Actions
before anything can be created. Create an IAM user (e.g.
`github-actions-deployer`) with programmatic access, attach
`AdministratorAccess` to get started (tighten later), and generate an
access key.

(The Terraform state bucket and the artifact bucket are the same S3
bucket, created automatically on first run — nothing to set up for those.)

---

## Step 1 — Add GitHub Secrets

**Settings → Secrets and variables → Actions → New repository secret:**

| Secret | Value |
|---|---|
| `AWS_ACCESS_KEY_ID` | from the IAM user above |
| `AWS_SECRET_ACCESS_KEY` | from the IAM user above |

That's the whole list. No `DB_PASSWORD`, `SSH_PUBLIC_KEY`, `EC2_SSH_KEY`,
`SSH_INGRESS_CIDR`, or `EC2_HOST` — those don't exist as secrets anymore:

| Old secret | What replaced it |
|---|---|
| `DB_USERNAME` | fixed default (`admin`) in `terraform/variables.tf`, override there if you want something else — not sensitive by itself |
| `DB_PASSWORD` | generated by Terraform (`random_password` resource), lives only in Terraform state (in your private, encrypted S3 bucket) and the instance's systemd service |
| `SSH_PUBLIC_KEY` / `EC2_SSH_KEY` | removed — no SSH key pair exists at all; deploy goes through AWS Systems Manager using the instance's IAM role |
| `SSH_INGRESS_CIDR` | removed — port 22 isn't open on the instance, so there's nothing to restrict |
| `EC2_HOST` | server IP flows directly from the Terraform job to the deploy job as a job output, in-run |

## Step 2 — Push

```bash
git add .
git commit -m "Full automation: infra + build + deploy, minimal secrets"
git push
```

Go to the **Actions** tab → `Full Deploy - Infra + Build + Deploy`. First
run takes ~5–8 minutes (VPC/RDS provisioning + server bootstrap + SSM
agent registration). When it's green, the app is live at the printed IP.

Every push after that re-runs the same thing: Terraform confirms infra is
unchanged (fast), then rebuilds and redeploys the app via SSM.

---

## Rollback

Every deploy leaves a timestamped backup on the server. To see them, or to
roll back manually, use **SSM Session Manager** (AWS Console → Systems
Manager → Session Manager → Start session → pick the instance) instead of
SSH — no key needed:
```bash
ls /opt/tomcat10/webapps/ROOT.war.bak-*
```
The pipeline also does this automatically if a deploy's health check fails.

## Troubleshooting

- **`AccessDenied` on `sts get-caller-identity`, `s3api create-bucket`, or
  `ssm send-command`** — the IAM user's policy doesn't allow those
  actions; `AdministratorAccess` covers it if you're not ready to write a
  scoped policy yet.
- **Deploy job stuck at "Wait for instance to be SSM-managed"** — the SSM
  agent (pre-installed on Amazon Linux 2023) needs the instance's IAM role
  to have propagated and the instance to have outbound internet access
  (it does, via the public subnet + IGW) — this step just needs a few
  extra minutes on a brand new instance.
- **Deploy script fails inside SSM** — the workflow prints
  `StandardOutputContent`/`StandardErrorContent` from the failed command
  in the Actions log; that's the real error from `/opt/deploy.sh` on the
  box (e.g. RDS not reachable yet, disk full, etc).
- **Docker push fails with permission error** — repo **Settings → Actions
  → General → Workflow permissions** → set to "Read and write permissions".

See `terraform/README.md` for infra-specific details (what gets created,
security notes, teardown).
